# Approach

## 1. Problem Understanding

The objective of this project is to allow a user to find a specific dialogue
inside an online video without manually watching the entire video.

The basic idea is:

- Take a video URL and a dialogue as input.
- Download and process the video.
- Extract the audio from the video.
- Convert the speech into a timestamped transcript.
- Search the transcript for the dialogue entered by the user.
- Identify the timestamp of the best match.
- Extract the corresponding video frame.
- Display the result to the user.

I treated the problem as a pipeline, where the output of one stage becomes the
input to the next stage.

## 3. High-Level Architecture

I divided the application into separate modules instead of putting the
entire processing logic inside the Flask application.

### `app.py`

Handles the Flask application, user requests and responses, and connects the
different processing stages.

### `video_processor.py`

Responsible for downloading the video and extracting its audio using
`yt-dlp` and FFmpeg.

### `transcribe.py`

Handles speech-to-text conversion using OpenAI Whisper.

The Whisper model is loaded once so that it does not have to be loaded again
for every search.

### `search_dialogue.py`

Handles searching for the user's dialogue inside the transcript.

This is where fuzzy matching is used to deal with small differences between
the user's input and the generated transcript.

### `templates/`

Contains the HTML templates used by Flask for the user interface.

Keeping these responsibilities separate made the application easier to
debug and modify.

## 4. Detailed Approach

### 4.1 Video Download

I used `yt-dlp` to handle video URLs.

Instead of implementing separate download logic for different video sources,
`yt-dlp` handles the downloading and format selection.

The downloaded video is stored locally because the same video may be searched
more than once.

I also use a hash of the video URL when creating cache-related paths. This
gives the same video a consistent identifier without using the complete URL as
a filename.

---

### 4.2 Audio Extraction

After downloading the video, I extract only the audio required for
transcription.

FFmpeg is used for this step.

The extracted audio is converted to:

- Mono audio
- 16 kHz sample rate

This gives Whisper a consistent audio format and avoids processing the video
itself during speech recognition.

The audio extraction logic is kept inside `video_processor.py`.

---

### 4.3 Speech-to-Text

I used OpenAI Whisper to convert the extracted speech into text.

An important part of the implementation is that the Whisper model is loaded
once rather than being loaded for every request.

Loading the model repeatedly would add unnecessary overhead and make every
search slower.

The transcription stage also provides timing information, which is important
because finding the dialogue text alone is not enough. The application also
needs to know approximately where that dialogue occurs in the video.

---

### 4.4 Dialogue Matching

Exact string matching would not be reliable for this problem.

The dialogue typed by the user may be slightly different from the text
generated by Whisper because of:

- Speech recognition errors
- Differences in punctuation
- Capitalization
- Small wording differences
- Missing or extra words

Because of this, I used `RapidFuzz` for fuzzy matching.

The search process compares the user's query against transcript segments and
selects the strongest matching segment.

The matching process also considers word-level similarity/coverage rather
than depending only on an exact phrase match.

The goal is not simply to find an identical string, but to find the transcript
segment that is most likely to represent the dialogue entered by the user.

---

### 4.5 Timestamp Identification

Once the best matching transcript segment is found, its timestamp is used to
locate the corresponding point in the original video.

If more precise word-level timing information is available, it can be used to
identify the beginning of the matching portion more accurately.

Otherwise, the timestamp of the matching transcript segment is used.

This step connects the text-searching part of the application back to the
actual video.

---

### 4.6 Frame Extraction

After obtaining the timestamp, OpenCV is used to extract the corresponding
video frame.

The timestamp is converted into the appropriate frame position using the
video's frame rate.

The resulting frame is then saved and displayed to the user along with the
matching timestamp.

This gives the user a visual confirmation of where the dialogue occurs.

---

### 4.7 Caching

Video downloading and transcription are the most expensive parts of the
pipeline.

If a user searches for multiple dialogues from the same video, repeating
these operations would be unnecessary.

To avoid this, the application caches processed data for previously handled
videos.

This allows later searches for the same video to reuse existing files instead
of starting the entire pipeline again.

The main idea is:

**First search:**

Video → Download → Audio → Transcription → Search

**Later search:**

Cached data → Search

This improves the experience considerably when the same video is searched
multiple times.

## 5. Why I Chose These Technologies

### Flask

The application mainly requires a small web interface and a few processing
routes, so Flask was sufficient for the project.

I did not need the additional complexity of a larger web framework.

### yt-dlp

It provides a practical way of downloading videos from supported online
sources without implementing separate download logic for each source.

### FFmpeg

FFmpeg is used specifically for the audio/video processing part of the
pipeline. It makes extracting and converting the audio straightforward.

### Whisper

Whisper provides local speech-to-text conversion and also provides timing
information that is useful for locating dialogue inside a video.

### RapidFuzz

A dialogue search should tolerate small differences between what the user
types and what Whisper produces. RapidFuzz provides a lightweight way to
perform this fuzzy matching.

### OpenCV

OpenCV is used to work with the actual video frames after a relevant
timestamp has been identified.

---

## 6. Design Decisions

One of the main design decisions was to keep the processing stages separate.

For example, the Flask application does not directly perform all the
transcription and video-processing logic. Instead, it calls the relevant
modules.

This makes it easier to:

- Debug individual stages.
- Change the transcription model later.
- Improve the search algorithm independently.
- Test video processing separately from the web interface.
- Understand the project quickly when looking at the source code.

Another important decision was to cache processed videos because repeatedly
downloading and transcribing the same video would be unnecessarily expensive.

---

## 7. Error Handling

There are several points in the pipeline where an operation can fail.

Some examples are:

- Invalid video URL
- Video download failure
- Video without usable audio
- FFmpeg failure
- Transcription failure
- Dialogue not found
- Very long videos taking too much time to process

I tried to handle these cases rather than assuming every input would be valid.

For external operations such as video downloading and FFmpeg execution,
failures are treated as possible runtime errors.

If the dialogue cannot be found, the application should return an appropriate
message instead of displaying an incorrect result.

---

## 8. Performance Considerations

The main performance bottleneck is the processing pipeline rather than the
Flask interface.

The expensive operations are:

1. Downloading the video.
2. Extracting and processing the audio.
3. Running Whisper transcription.

Caching helps avoid repeating these expensive operations for the same video.

The current implementation is intended for the scope of this assignment and
keeps the architecture relatively simple.

For a larger production system, the transcription process would be better
handled asynchronously using a background worker so that the web request does
not remain blocked during long processing operations.

---

## 9. Assumptions

The current implementation assumes that:

- The provided video URL is valid and accessible.
- The video contains reasonably clear spoken dialogue.
- Whisper can transcribe the audio with sufficient accuracy.
- The dialogue being searched for is actually present in the video.
- The video can be downloaded and processed locally.

These assumptions can affect the accuracy and response time of the
application.

---

## 10. Limitations

The current implementation has a few limitations.

### Transcription accuracy

The result depends on the quality of Whisper's transcription. Background
noise, accents, overlapping speech and unclear audio can affect the result.

### Processing time

Long videos can take considerable time to download and transcribe.

### Similar dialogues

If the same or very similar dialogue occurs multiple times, the application
may return the strongest matching occurrence rather than every occurrence.

### Spoken dialogue

The approach is primarily designed for spoken dialogue. It is not intended
to perform general music or background-audio search.

### Local processing

The current implementation performs the computationally expensive processing
locally, which limits how efficiently it can scale to many simultaneous users.

---

## 11. Possible Improvements

If I were extending the project further, some improvements I would consider
are:

- Use `faster-whisper` for faster transcription.
- Add GPU support when available.
- Add progress updates for long-running operations.
- Improve transcript indexing for faster searches.
- Add automated tests for the individual processing stages.
- Add better cache management and cleanup.

I would prioritize these based on the actual requirements rather than adding
complexity unnecessarily.

---

## 12. Final Summary

The application follows a simple processing pipeline:

**Video URL → Video → Audio → Transcript → Dialogue Match → Timestamp → Frame**

The main focus of the implementation was to make each stage understandable
and independent while avoiding unnecessary repeated processing.

The combination of Whisper for speech recognition, RapidFuzz for dialogue
matching, and OpenCV for frame extraction allows the application to connect a
user's text query back to the corresponding location in a video.
